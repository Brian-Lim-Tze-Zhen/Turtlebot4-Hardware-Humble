## What Has Been Tried (and Why It Failed)

### Attempt 1: "BlockedHold cannot be ported"
- **What:** The first answer said Humble cannot do BlockedHold.
- **Why it failed:** Only `polygon_sub_topic` was checked, and it is absent in Humble collision monitor 1.1.20. `<polygon>.enabled` IS dynamically settable in Humble (tested). Fixed square + enabled switch = same behaviour, because the sim square is always ±1.6 m in base_link.

### Attempt 2: Collision monitor YAML in the hardware config
- **What:** The hw YAML had a `collision_monitor:` block copied from sim.
- **Why it failed:** The Humble bringup (nav2_bringup 1.1.20 `navigation_launch.py`, turtlebot4_navigation 1.0.5) never starts the collision monitor. The 5 Oct bags have no collision_monitor node, so FootprintApproach was never active on the robot. Fixed by the `*_cm` launch copies. Humble also uses `max_points` (= Jazzy `min_points` − 1), not `min_points`.

### Attempt 3: Shutdown release of the hold
- **What:** In the `finally`, set hold false and spin the future.
- **Why it failed:** The 0.2 s timer fired during `spin_until_future_complete` and re-enabled the hold. Also, rclpy's default signal handler shut down the context before `finally`. Fixed: `destroy_timer` first, `rclpy.init(signal_handler_options=SignalHandlerOptions.NO)`, SIGTERM → KeyboardInterrupt.

### Attempt 4: Fire-and-forget parameter set
- **What:** `call_async` without checking the reply.
- **Why it failed:** Before the collision monitor is configured, the param is not declared ("cannot be set because it was not declared"). The node believed it was sent. Fixed with `on_hold_reply`, which resets `hold_state` so the next tick resends.

### Attempt 5: First explainer page with the old ellipse
- **What:** The page showed a long predicted-path ellipse for walkers.
- **Why it failed:** The final config uses body disk 0.30 + a 0.6 m stub, set by the `*hwreq*` case in `run_headon_F_trial.sh`. The page was corrected (version 4).
